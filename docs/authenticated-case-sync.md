## Client contract

`public.sync_case_records(changes jsonb)` returns a JSON array. Each submitted change is `{table_name, row, expected_version, mutation_id}`. The row includes UUID `id` and authenticated `user_id`; case-owned records also include `case_id`. New records use expected version `0`. Each successful result is `{table_name, record_id, version, mutation_id}`. Supported tables are `cases`, `children`, `people`, `entries`, `attachments`, `court_orders`, `court_order_provisions`, `filing_packages`, `key_dates`, `pattern_tags`, `advisor_threads`, `ai_outputs`, and `case_workspace_state`.

- Batches contain at most 1,000 changes and commit atomically. Per-owner transaction locks serialize overlapping batches. A stale expected version fails with SQLSTATE `P0001`, message `SYNC_CONFLICT`, and record details; the server does not overwrite the winner.
- Every successful mutation ID retains its original request and response in a private receipt table. Replaying the same request returns the original receipt even after later edits. Reusing that ID for different content fails with `MUTATION_ID_REUSED`. Clients must retain the original request and ID until acknowledgement, and create a new ID for a newly chosen conflict resolution.
- Unknown tables and columns fail closed. Server provenance fields are rejected. Identifiers are selected from a fixed table allowlist and quoted as identifiers; row values use parameters. Updates preserve omitted columns; an explicit JSON null clears a nullable column. The server controls `updated_at`.
- Existing rows without a corresponding sync version fail with `SYNC_CONFLICT`; this migration does not silently adopt or overwrite legacy data. The inspected target had no Auth users. A populated target needs an explicit legacy-data conversion before enabling this client.
- `case_workspace_state` is one row per account with `id = user_id`. Its `state` is an object for UI state such as report versions, filing links, pattern decisions, and advisor metadata. The client must sanitize this state before submission; the database does not interpret or authorize arbitrary identifiers embedded within this owner-private JSON object.

`public.read_case_workspace()` takes no arguments and returns `{snapshot, versions, workspace}`. It is a SECURITY INVOKER, STABLE function. One SELECT gathers every collection, its version records, and the workspace row using one PostgreSQL statement snapshot. The snapshot keys match `CaseIntelligenceSnapshot`: `cases`, `children`, `people`, `entries`, `evidenceAttachments`, `courtOrders`, `courtOrderProvisions`, `filingPackages`, `keyDates`, `patternTags`, `advisorThreads`, and `aiOutputs`. Collections and versions are arrays; workspace is its full row or null. Soft-deleted rows remain available to sync clients for deletion and recovery state.

The read RPC does not paginate. It rejects more than 25,000 snapshot records, more than 25,001 version records, or more than 32 MiB of serialized JSON with `WORKSPACE_TOO_LARGE`. Per-table sentinel limits detect overflow; it never returns a partial workspace. These are explicit beta implementation limits, not established scale guarantees. Large row values still consume memory before the serialized-size check. Pagination must preserve a common snapshot/version boundary before this limit is raised.

## Authorization and originals

Both public RPCs use SECURITY INVOKER. The fixed write wrapper calls private SECURITY DEFINER code with an empty search path. **Keep `fb_private` out of PostgREST exposed schemas.** Trusted `auth.users.email_confirmed_at` and `auth.uid()` establish the account; editable user metadata and profile roles do not authorize access. A missing profile is created from the verified Auth email with generic display label `Parent`, preserving existing profile details.

The migrated case tables, join tables, profile, workspace, versions and revisions have owner and verification restrictions for reads, restrictive denial policies for direct writes, and explicit grants. These restrictive guards continue to apply in the presence of older permissive policies. A private per-record transaction marker allows only the sync implementation to write case records, so an older SECURITY DEFINER writer cannot bypass version checks. Cross-record checks require each child, person, entry, source attachment, order, provision, filing, advisor thread, and AI output link to belong to the same owner and case. The exposed RPC accepts no arbitrary SQL or table identifier beyond its fixed allowlist.

`evidence-originals` is private with a 25 MiB upload limit. Original paths are `user_id/case_id/entry_id/attachment_id/original`. Authenticated insert and select require a verified owner and a live owning case and entry. Update and delete are denied for this bucket even if an older permissive storage policy exists. Attachment rows require an entry, that exact path, `sha256`, a lowercase 64-character hash, and a size of 1 through 26,214,400 bytes. Once synced, the attachment row is immutable; replaced bytes need a new attachment identity. Storage insertion can precede attachment metadata, but not its owning case or entry. This migration validates ownership and hash format; the client evidence module hashes and verifies actual bytes. No server-side attestation of original byte contents is implied.

Every entry mutation records previous and current server snapshots, the client-supplied content hashes, a server-computed snapshot hash, a chained revision hash, mutation ID, version, and server receipt time. Clients can select their revisions but cannot insert, update, or delete them. The first accepted `metadata.captured_body` is immutable, with a fallback to the first submitted body if omitted; original voice transcript, capture method, source mode and capture version are also immutable. Reviewed body text and review metadata can change while preserving the source. These records establish what the server received and when; they do not establish the truth of an observation, prove a user-supplied event time, or independently attest the client-supplied content hash. Admin/database deletion and account-retention policy remain separate product decisions.

## Restored-schema compatibility

The April project schema uses `profiles(id)` for several owner foreign keys; May-created tables use `auth.users(id)`. The migration preserves both and provides verified profile creation before the first case write. It widens existing CHECK constraints to retain legacy entry/capture/mood/flag, case status, filing, date, and order values while accepting the current app's values, including `voice_local`. It makes the legacy required court-order date nullable so a manual order need not invent a date. It does not relabel old enum values, infer legal identities, or migrate the legacy `parties` table into `people`.

The composite conditionally revokes API-role EXECUTE on the existing `public.rls_auto_enable()` event function. It preserves the function and enabled event trigger. The public `vector` extension remains in place: read-only dependency inspection found `legal_knowledge_base.embedding` and `idx_legal_kb_embedding`, so relocating this unrelated extension requires a separate compatibility review. The extension-location advisor warning is not claimed resolved.

[`tests/db/inspected-schema.json`](../tests/db/inspected-schema.json) stores schema metadata only, with no user rows. The fixture generator rebuilds inspected overlapping table columns, defaults and constraints, and minimal referenced objects; it is not a full dump of Supabase services. Other historical product tables and features are outside this focused migration's write API.

## Reproducible local checks

Run `bash scripts/test-db.sh` with PostgreSQL 14+ installed. Set `FAMILY_BENCH_PG_BIN` if its binaries are outside the normal path. The script creates a disposable cluster under `/tmp`, binds only a private Unix socket, rejects TCP host authentication, and removes the cluster on exit. It never connects to Supabase or uses real records. Sandboxed environments may need permission to use local PostgreSQL shared memory.

The suite applies the exact active composite once against a fresh schema and again against the inspected April fixture. Minimal local Auth and Storage schemas reproduce roles, ownership, and RLS, not the managed services themselves. Actual separate database connections test overlapping edits and reads before/after commit. Both suites passed on 2026-09-04 with:

- Verified owner access, second-owner isolation, unverified and anonymous denial, cross-case source/link rejection, and attempted SQL/table and field injection.
- All 13 supported table kinds, profile creation, current capture values against legacy constraints, omitted-field preservation, whole-batch rollback, exact mutation replay, reused-ID rejection, and stale/concurrent conflict preservation.
- Original capture/transcript immutability, revision snapshots and hash linkage, attempted direct revision insertion, accidental DML regrants, and a deliberately granted older SECURITY DEFINER writer.
- Linked private original upload/read, size validation, denied overwrite/delete despite a permissive storage policy, and byte access revoked/restored by parent soft deletion/restoration.
- Atomic complete workspace reads, empty foreign-owner reads, and matching content/version pairs during and after concurrent commits.
- The managed RLS event function loses API-role execute privileges while its event trigger remains enabled.

Remote application is complete. Managed Storage byte upload/download, deployed Auth confirmation/redirect behavior, client conflict recovery, and a complete capture-to-export round trip still require separate integration checks. Passing the local SQL suite alone does not establish production readiness.
