| Dimension | Established contract |
| --- | --- |
| Character | “Modern court”: credible, restrained and calm for a parent preparing records under stress. Paper/ink surfaces, clear factual hierarchy and little ornament. |
| Color | Paper `#F7F6F3`, ink `#14181F`, oxblood `#B44028`, forest `#2F5A3A`, sand `#C9B892`, amber `#A76A14`. Use semantic Family Bench tokens. Reserve urgency colors for actual urgency, not routine sync trouble. |
| Type | Inter is the primary UI family at 400/500/600. Instrument Serif is used sparingly for captions, legal formality and quiet asides. JetBrains Mono carries dates, case numbers and compact references. Existing body/small/micro tokens are 14/12/10.5; readability changes require deliberate token or role adjustments. |
| Composition | Left-aligned kicker → title → body → actions; 4pt spacing; paper tone shifts and hairlines; established 8/12/14/18 radii. No new palette, UI kit, icon pack, decorative gradient, background imagery or heavy card shadows. |
| Icons | Existing inline SVG/currentColor Family Bench icon vocabulary, consistent rounded strokes. No emoji controls. Prototype provider logos and court seals are stand-ins and need actual assets before any corresponding feature ships. |
| Motion | Reference timing is 150/220ms with soft ease-out. Small meaningful feedback only; no page-load spectacle, parallax or springy overlays. Respect reduced motion. |
| Mobile | One-handed capture and focused review, generous controls, safe-area/keyboard clearance, clear progress and a reachable primary action. |
| Desktop | Organize, compare and prepare with compact rows, persistent filters and relevant inspectors. Use simultaneous context where it improves the task. |
| Shared behavior | Same records, permissions, persistence, source preservation and export rules on every surface. Layout adaptation cannot fork business logic. |
| Copy | Sentence case, second person, active voice and factual language. Distinguish original source, reviewed text and private notes. Never infer a legal conclusion or advertise unavailable protection. |

The design README contains prototype examples asserting legal strength or independent timestamp protection. Their visual treatment can inform hierarchy; the claims cannot be reused without the corresponding supported behavior and review. The guardrails' factual-copy and no-false-reassurance rules control. A “Court-ready” label in current code is a visibility flag, not a legal certification; the production wording needs to express sharing eligibility precisely.

## Phased screen priorities

Each phase ends with a usable workflow and recorded checks. The order favors the first real user's journey over polishing placeholder capabilities.

| Phase | Screens and concrete work | Acceptance criteria |
| --- | --- | --- |
| 1 — Entry and recovery | Auth, email verification/reset, case setup, workspace status and shared controls. Initial control semantics, input labels, Home/shell clarity and contrast changes are implemented. Verify focus, busy/error recovery and assistive-technology behavior end to end. | A keyboard and screen-reader user can sign in, understand verification, correct input, retry a failed save and identify the current case. Error copy explains the next action without exposing another account or losing its pending work. Every visible control acts or clearly states why unavailable. |
| 2 — Capture and source review | Manual/voice capture, attachment staging and Entry Detail. Preserve the working six-step flow. Make case/child context, optional fields, source versus reviewed text, attachment progress and partial-save recovery explicit. Present source/review alongside provenance on wide screens; stack them clearly on mobile. | A user records an event, sees which files were saved, recovers from a failed attachment, and reopens the same entry without duplication. Back/cancel and unsaved-draft behavior are explicit. No automatic transcript, GPS, verification or AI claim appears without evidence. If child selection is added, it must actually control the saved record; current first-child inference must not be disguised by a cosmetic selector. |
| 3 — Factual export | Reports → export preparation, entry selection, date controls, source preview, PDF/ZIP progress and result. Keep PDF primary and original-file ZIP a distinct action with explicit sensitive-content review. | Selection count, date range, excluded private records and original-file count match the resulting artifact. A user can tell whether a PDF or original-file packet was created. Missing/hash-mismatched files block the corresponding packet with a recoverable explanation; busy states prevent duplicate submission. No official-form or court-acceptance claim. |
| 4 — Case organization | Home, Evidence, Timeline and Case Map. Standardize existing row metadata, selection, filters, date groups and inspector rhythm. Make actual case context and useful next actions visible. Adapt tablet navigation/panels without changing shared state. | At 768/1024/1180px, primary content remains readable and controls reachable without accidental page overflow. Filters/selection survive detail-back navigation. Case Map clearly distinguishes saved orders/provisions/dates from future document extraction. Desktop comparison is faster without shrinking essential text below readability requirements. |
| 5 — Broader workspaces | Filing builder, Patterns, Advisor, integrations, practitioner and safety surfaces, when their product capabilities are implemented. Apply the established rail/list/inspector language as each feature becomes real. | Each surface exposes only supported actions and truthful statuses. AI/legal guidance, sharing permissions, e-filing and safety behavior have their own implementation/evaluation gates. Visual fidelity never substitutes for capability. |

Proposed mobile navigation work belongs in Phase 4: compare the current six destinations with a five-item capture-centered arrangement, using an existing destination such as Case Map or another explicit workspace entry for secondary routes. Keep deep links, predictable back behavior and access to Reports/Case Map. The final labels/grouping need a dedicated interaction review; this plan does not silently choose or implement them.

## Shared interaction and visual acceptance

- **Brand:** use existing tokens/primitives, consistent square evidence marks and mono references, hairlines and restrained paper surfaces. No per-screen palette/font invention. Token adjustments needed for contrast are documented once and checked across light-theme surfaces.
- **Readability:** essential normal text reaches 4.5:1; larger text and meaningful graphical boundaries reach 3:1 where applicable. Required information cannot depend on color alone. Long filenames, case captions, localized-length strings and errors wrap or expose an accessible full value. Assess 16px mobile input/reading roles while retaining the established hierarchy.
- **Touch and keyboard:** at least 44×44pt targets, with 48dp Android targets where needed; small visual controls get sufficient hit area. Visible focus, logical tab order, useful labels and selected/expanded/disabled/busy state announcements. Keyboard submit and focus after validation work. No gesture-only critical actions.
- **Layout:** verify 375/390/430px phone, 768px tablet, 1024/1180px intermediate desktop and 1440px wide desktop, plus landscape. Fixed chrome and keyboards cannot cover the last input, error or primary action. Context rails collapse or relocate before squeezing the main task. No arbitrary change to a different store or save path at a breakpoint.
- **States:** record empty/new-account, loading, local-save success, queued sync, synced, expired session, storage full/failure, upload failure, conflicting edit, missing original and completed export. A status says what is known and provides the relevant next action. Routine caution must not resemble a safety alarm.
- **Motion and accessibility settings:** reduced motion and large system text retain complete function and reading order. No clipping of multi-line labels or errors. Test VoiceOver/TalkBack and browser keyboard/screen-reader behavior on the chosen release surfaces. Dark mode is not established by the current light-only tokens; do not claim a supported dark theme until it has its own token and contrast verification.
- **Performance:** large evidence lists retain responsive search/selection and scroll. Inspect list virtualization and image thumbnail loading once representative record volumes exist; placeholder record counts are not a performance test. Export generation displays progress and allows a clear recovery path.
